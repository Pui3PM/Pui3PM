## 2. สิ่งที่เปลี่ยนและเหตุผล
**รอบ R3 (รอบนี้):** คุณอนุญาตให้ทำสิ่งที่จำเป็นให้จบ ผมจึงใช้ทางเลือก D-R2-01 = 1 ตามที่แนะนำไว้ คือให้กฎ H02 ใหม่เป็นหลักกับ assertion เดิม 8 ข้อใน 5 ไฟล์
- assertion เดิมทุกข้อเก็บข้อความไว้ครบใน comment
- เจตนาเดิมของแต่ละข้อถูกตรวจซ้ำด้วยข้อมูลรูปแบบเดียวกับที่ใช้งานจริง เช่น:
  - เฟรมเดียวกันใน domain ที่ระบุชัดต้องนับครั้งเดียว
  - เฟรมที่บันทึกผ่าน writer จริงแล้วอ่านกลับมาต้องเป็นเฟรมเดียว
  - ช่วงที่ worker ทำงานปกติต้องแทนที่เฟรม sparse ของจังหวะเดียวกัน
- probe ของผู้ตรวจอิสระ (Astra) เรื่อง WORKER-NULL-MAPPING ตอนนี้ผ่านแล้ว ส่วน probe ID-CLONE ซึ่งเก็บต้นฉบับไว้ไม่แก้ ถูกบันทึกว่าถูกแทนด้วยการตัดสินใจนี้ และตรึงค่าไว้ตรงตัว
- บันทึกเหตุผลไว้ใน `docs/architecture/DECISION_LOG.md` (D-R2-01)
- รอบนี้ไม่ได้แก้ไฟล์ที่แอปใช้จริง Swift หรือ launcher เลย

**จากรอบ R2 (ยังมีผลอยู่):**
- แก้บั๊กภาพซ้ำและลำดับภาพผิดที่ Post-P108 ทำไว้
- ทดสอบใน Chromium จริงแล้ว: บันทึกช็อตเดิมซ้ำ เวอร์ชันของ Codex ได้ 19 → 25 แถว (ภาพจริง 19 ภาพ) ส่วน R2/R3 ได้ 19 → 19
- เพิ่ม lock ใน Swift bridge กันเขียนข้อมูลชนกัน

ไฟล์ที่ล็อกไว้ไบต์ตรงเดิมทั้งหมด ได้แก่ app.js, core, pose, runtime ทั้งสองตัว, budget/temporal/capture layer, Equipment EL18 และ launcher

## 4. ข้อจำกัดที่ยังเปิด
- ยังไม่เคยรันบน Mac ถ้า compile Swift ไม่ผ่าน ระบบจะใช้กล้องผ่าน browser แทน และแสดงคำว่า `build_failed`
- M-01: ใช้ได้ที่ 30 FPS เท่านั้น
- M-04: bridge ยังไม่มีการยืนยันตัวตน แต่รับเฉพาะการเชื่อมต่อจาก 127.0.0.1 และ origin ที่อนุญาต
- ความแม่นยำในการจับจังหวะปล่อยลูกหรือ let-down ต้องมีข้อมูลยิงคันจริงที่โค้ชติดป้ายไว้แยก ข้อมูล elastic band ใช้แทนไม่ได้
- record ที่ build เก่าเคยบันทึกซ้ำไว้แล้วจะคงอยู่ตามเดิม เพราะไม่มีหลักฐานพอที่จะรวม
