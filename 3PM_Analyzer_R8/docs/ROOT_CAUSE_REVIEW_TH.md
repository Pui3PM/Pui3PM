# ผลตรวจปัญหา Shot Process และภาพ 25 ช่อง — R7

ตรวจจาก ZIP EL18 และ Trace 30 กันยายน 2026 เวลา 23:42 น. ประเทศไทย ไม่ได้ตรวจจากรุ่นเก่าแทนไฟล์ที่แนบ

**สถานะ: แก้ข้อผิดพลาดที่ทำซ้ำในซอฟต์แวร์ได้แล้ว แต่ยังไม่ปิดข้อร้องเรียนการลดแขนแล้วถูก Cap ในการทดสอบจริง** เพราะยังไม่ทราบว่าเป็น shot หมายเลขใดใน 3 shots ที่บันทึก การวินิจฉัยจากท่าที่ตัวจำแนกตัดสินแล้ว ไม่ใช่หลักฐานอิสระว่าปล่อยจริง

## เกิดอะไรขึ้น

- Trace มี 9 รอบการเคลื่อนไหว มี 3 เหตุการณ์ capture_committed และมีหลักฐานภาพ 3 records ไม่ใช่หลักฐานว่าควรจับครบทั้ง 9 รอบ
- ทั้ง 3 records มี 25 frames แต่หน้าภาพใช้ฐานข้อมูล thumbnail อีกชุดที่เริ่มจาก 15 ภาพ ตัวเติมภาพเป็น best effort สามารถหมดเวลา/ยกเลิก/ข้ามงานได้ จึงเกิด “ข้อมูล 25 แต่เห็น 15” ตามที่ผู้ใช้รายงาน
- Shot ที่บันทึกหมายเลข 2 ขาด Hold ตาม contract แม้มี timestamp ของภาพอยู่ในช่วง Hold สาเหตุเชิงโค้ดคือการเลือก Hold จำกัดที่ป้าย hold-pin/aim-hold ในขณะที่ encoder ใช้ release-focus หรือ anchor-focus ทับช่วงเดียวกันได้ Trace เดิมไม่มีป้ายของแต่ละภาพ จึงทดสอบด้วย timestamps จริงและป้ายจำลองหลายแบบ ไม่อ้างว่าเล่นภาพจริงซ้ำแล้ว
- ทั้ง 3 records ไม่มี followThroughEndEpochMs และไม่มีภาพ recovery-end ทั้งที่ cycle มี recovery อยู่หลัง T0 ประมาณ 3324, 1464 และ 1637 ms ตามลำดับ ภาพสิ้นสุดที่ +769, +774 และ +885 ms
- พบช่องเขียนทับข้อมูล: temporal enrichment อ่าน record แล้วเขียนตรง ขณะที่ Recovery ใช้คิวอีกทาง ถ้า temporal เขียน snapshot เก่าทีหลังจะลบข้อมูล Recovery ได้ ทดสอบบังคับลำดับนี้แล้วพบปัญหาจริง แต่ Trace ไม่มี log ของการเขียนฐานข้อมูลทุกครั้ง จึงยังระบุไม่ได้ว่าเกิดการแข่งขันนี้ครบทุก shot หรือไม่
- พบการใช้ releaseEventId จับคู่ Recovery ทั้งที่เลขนี้กลับไปเป็น 1 หลัง rearm จึงมีโอกาสเอา early Recovery ของรอบก่อนมาต่อกับ shot ใหม่
- รอบ cycle-1790786394166: adaptive ยืนยัน release แต่ Foundation ยังยืนยันเพียง Setup/Set/Draw แล้ว veto เหตุการณ์นั้น นี่คือความไม่สอดคล้องระหว่าง state machines ไม่ใช่ข้อพิสูจน์ว่ารอบนี้เป็น release จริง ห้ามแก้ด้วยการบังคับให้ผ่านโดยไม่รู้ ground truth
- ผู้ใช้ยืนยันว่ามีหนึ่ง shot ถึง Expansion แล้วลดแขนเร็ว แต่ถูก Cap: ถือเป็น false positive ที่ยังเปิดอยู่ ยังไม่กำหนดให้ shot 1/2/3 ใดเป็นกรณีนั้นโดยเดา
- พบช่องโหว่ใน native terminal acceptance: positive proof ที่ cache ไว้และ strong motion สามารถข้ามข้อมูล collapse/lowering ก่อน commit ได้ R7 ตรวจข้อมูลขัดแย้งก่อนผ่านทุกทางของ branch นี้ ไม่เปลี่ยน threshold ความไว
- Trace รุ่นเดิมรายงานชื่อ R6_CleanPackage ทั้งที่ ZIP เป็น EL18 ทำให้เทียบรุ่นผิดได้ แก้ชื่อรุ่นและ cache identity แล้ว

## ทำไมแก้แล้วปัญหาจึงวนกลับมา

1. มีหลายเจ้าของคำตัดสิน: lifecycle, adaptive, Foundation, capture และ persistence ใช้คำว่า “ผ่าน” คนละจุด ไม่ได้มีสถานะธุรกรรมเดียวตั้งแต่ตรวจพบจนบันทึกสำเร็จ
2. มีสองแหล่งภาพ: fixed25 Replay กับ 15-frame coach thumbnails การทดสอบจำนวนในฐานข้อมูลไม่รับรองจำนวนที่หน้าจอ
3. งาน async เขียน record เดียวกันผ่านคนละทาง และรหัส event นำกลับมาใช้ได้
4. ป้ายช่วงเก็บภาพถูกใช้แทนช่วงท่าจริง ทำให้เพิ่มจำนวนภาพแล้วยังขาด stage
5. ชุดทดสอบเดิม 93 ไฟล์ผ่านทั้งหมดบน source EL18 แต่ไม่ครอบคลุม DOM filmstrip จริงตาม renderer, stale-write ordering, reused event ids และ positive cache ที่ถูกหักล้างก่อน commit
6. Fixtures เก่าบางชุดมีชื่อ real_bow โดยไม่ได้พิสูจน์ชนิดอุปกรณ์ ผู้ใช้ชี้แจงว่าการทดสอบวันก่อนใช้ elastic band การใช้ชื่อ fixture เป็น ground truth จะทำให้ปรับความไวผิดทิศ

## แก้ใน R7 แล้ว

- แทนที่ตัวเติม thumbnail ที่ยกเลิกได้ด้วย filmstrip ที่อ่าน record เดียวกับ Replay แสดง 25 ช่องทุก role; มีภาพจริงเท่าไรแสดงเท่านั้น ช่องที่เหลือระบุ Missing; กดขยายภาพได้ ป้องกัน record คนละ release และผลอ่าน async ที่กลับมาหลังเปลี่ยน shot
- รวม temporal writer เข้าคิว evidenceDbMerge เดิม ไม่สร้างระบบกล้องใหม่ แก้ null mediaTime ไม่ให้กลายเป็น 0 จนรวมภาพคนละเวลา
- จับคู่ Recovery ด้วย release epoch ที่ตรงกัน รับทั้งกรณี Recovery มาก่อน/หลังสร้าง shot; ไม่รับ auxiliary เป็นตัวจบ Side และเก็บ context ไว้เมื่อเขียนล้มเหลวพร้อม retry แบบจำกัด
- เลือก Hold จากภาพจริงในช่วง Hold ที่พิสูจน์ได้และเป็นคนละภาพกับ Anchor ไม่กิน expansion-pin เป็น Hold; เมื่อรู้ว่า Recovery เกิดแล้วแต่ไม่มีภาพ ให้ขึ้น INCOMPLETE
- รักษาภาพที่ contract เลือกเป็นตัวแทนแต่ละ stage ก่อนแบ่ง quota 25 ภาพ ไม่ปล่อยให้การลดจำนวนเพื่อความหนาแน่นทิ้งหลักฐานสำคัญ
- ปิดช่อง positive cache ข้าม contradictory collapse/lowering ใน native terminal branch; ไม่ผ่อน Foundation และไม่เปลี่ยนเกณฑ์ระยะมือเพื่อไล่จับ shot เพิ่ม
- ให้ Live Evidence และรายการ calibration อ่านผล contract ล่าสุดหลังบันทึก รวมถึงถอดสถานะครบที่ค้างเมื่อ record ล่าสุดไม่ครบ
- เพิ่ม Foundation veto ลง event log และ per-frame timestamp/tag/source ลง Trace ให้ตรวจซ้ำได้
- เก็บ EL18 catalog 683 รายการและไฟล์ frozen ทุกตัวเหมือนต้นฉบับ มี launcher สาธารณะเพียง START_3PM.command

## ยังไม่แก้/ยังไม่รับรอง

- ยังไม่พิสูจน์ว่า false positive รอบที่ผู้ใช้รายงานถูกแก้แล้ว ต้องทราบหมายเลข shot หรือดูวิดีโอที่ระบุการปล่อย/ลดแขน การลดแขนหลังปล่อยจริงกับการลดแขนโดยไม่ปล่อยต้องทดสอบแยกกัน
- Foundation/lifecycle ยังอาจ veto ไม่ตรงกัน R7 เพิ่มความสามารถตรวจสอบ ไม่บังคับรับรอบนั้น
- capture_committed ใน trace เดิมคือการส่งผ่านชั้น CaptureIntegrity ไม่ใช่ใบยืนยัน backend persistence สำเร็จทุกขั้น ระบบยังต้องพัฒนาสถานะ accepted/saving/saved/evidence-finalized ให้ชัดในงานต่อไป
- ไม่มี raw landmarks, ภาพ/วิดีโอและ finger/string separation ของทุกกรณี จึงไม่สามารถย้อนพิสูจน์การปล่อยจริงจาก Trace อย่างเดียว
- Native Mac camera/BLE/GUI และความแม่นยำ live bow ยังไม่ได้ทดสอบจาก Linux ห้ามเรียกชุดนี้ว่าหายขาดหรือผ่านสนามจริง

## เกณฑ์ปิดงานที่ป้องกันปัญหากลับมา

ทุก defect ต้องมีกรณีที่ทำให้รุ่นเก่าล้มเหลวและรุ่นใหม่ผ่าน พร้อมชุดทดสอบเดิม ห้ามลบหรือผ่อน negative controls เพื่อให้ผ่าน

สำหรับ detector ต้องมีวิดีโอ/label ราย shot ที่แยก: ปล่อยจริงปกติ, ปล่อยสั้นใกล้หน้า/หู, Expansion แล้วลดแขนเร็วโดยไม่ปล่อย, let-down ช้า, บังมือ, tracking หาย, กล้องหลุดต่อใหม่ และหลาย shots ต่อกัน ทดสอบ band และ bow แยกชุด รายงาน false positives, misses, duplicates และความคลาดเคลื่อน T0 ตามจริง ยังไม่มีจำนวนรอบที่เพียงพอให้ประกาศ zero-error ในทุกสภาวะ

สำหรับ pipeline ต้องตรวจพร้อมกันว่าเหตุการณ์หนึ่งสร้าง shot เดียว, บันทึกสำเร็จ, Recovery ต่อกับ shot ถูกตัว, contract ไม่หลอกว่าครบ, Replay กับ filmstrip ใช้ภาพเดียวกัน และทุก shot แสดง 25 ช่องพร้อมสถานะ Missing ที่ตรงจริง

การปล่อยรุ่นต่อไปต้องยึด R7 + EL18 นี้เป็นฐาน ไม่ย้อนคัดลอกทั้งไฟล์จากรุ่นเก่าเพื่อแก้จุดเดียว กฎอยู่ใน AGENTS.md และมี checksum/distribution gate ตรวจไฟล์ส่งมอบ
